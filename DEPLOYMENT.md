# Deploying FinSight AI

Backend: **FastAPI on Render** (Python 3.14, Gunicorn + Uvicorn worker).
Frontend: **Vite/React on Vercel**. Database: **MongoDB Atlas**. AI: **Groq**.

## 1. MongoDB Atlas
1. Create a cluster (the free M0 tier works) and a database user.
2. Network access: allow Render's outbound IPs (or `0.0.0.0/0` while testing).
3. Copy the `mongodb+srv://…` connection string.

Indexes are created automatically on startup, including a TTL index that expires AI cache entries.

> **Existing data:** on first boot the backend migrates old month-name records (e.g. `"Jan"`) into
> `YYYY-MM` periods and builds transactions from them. The migration is idempotent and additive, but
> **take an Atlas snapshot/backup before the first deploy** of this version.

## 2. Backend on Render
**Blueprint (recommended):** Render → New → Blueprint → select this repo. `render.yaml` defines the
service. You'll be asked for the secrets marked `sync: false`:

| Variable | Value |
|---|---|
| `MONGODB_URI` | Atlas connection string |
| `GROQ_API_KEY` | from console.groq.com |
| `ALLOWED_ORIGINS` | JSON list of frontend origins, e.g. `["https://fin-sight-ai-intelligent-financial.vercel.app"]` |

`JWT_SECRET_KEY` and `DIGEST_CRON_SECRET` are generated by Render. `ENV=production` turns on strict
startup checks (strong JWT secret, no DEBUG, no wildcard CORS, Groq key present): a misconfigured
deploy fails fast instead of running insecurely.

**Manual service instead:** root directory `backend`, build `pip install -r requirements.txt`,
start `gunicorn app.main:app -c gunicorn.conf.py`, health check `/api/health`, env `PYTHON_VERSION=3.14.2`.

**Docker (any host):**
```bash
docker build -t finsight-api backend
docker run -p 8000:8000 --env-file backend/.env finsight-api
```
Add `--build-arg WITH_EMBEDDINGS=1` for semantic RAG search.

### Optional settings
| Variable | Default | Notes |
|---|---|---|
| `GROQ_CHAT_MODEL` / `GROQ_FAST_MODEL` | `openai/gpt-oss-120b` / `openai/gpt-oss-20b` | Groq retires models; check `GET /openai/v1/models` if chat starts failing |
| `GROQ_VISION_MODEL` | `qwen/qwen3.8-27b` | receipt scanning |
| `GROQ_SPEECH_MODEL` | `whisper-large-v3-turbo` | voice input |
| `JWT_EXPIRATION_MINUTES` | 60 (1440 in `render.yaml`) | session length |
| `RATE_LIMITS_ENABLED` | `true` | per-user/IP limits; in-memory, so per instance |
| `WEB_CONCURRENCY` | 1 | each worker holds its own ML/RAG indexes |
| `FINSIGHT_DISABLE_EMBEDDINGS` | unset | force BM25-only retrieval |

**Memory:** the default install fits Render's 512 MB free tier. Semantic RAG search (`requirements-rag.txt`,
`fastembed`) adds ~250 MB: use a 1 GB+ instance for it. Without it, retrieval uses BM25 with heading boosts
and acronym expansion (hit@3 = 100% on the retrieval eval set).

**Free-tier cold starts:** Render free services sleep after inactivity; the first request takes ~30–60 s.
The frontend keeps cached sessions and retries gracefully, but a paid instance avoids this.

### Weekly digests (optional)
Digests are built on demand when a user opens the app. To pre-build them weekly, add a Render Cron Job
(or GitHub Actions schedule) that runs:
```bash
curl -X POST https://<your-api>/api/ai/digests/run -H "X-Cron-Secret: $DIGEST_CRON_SECRET"
```

## Backend-first startup

The site must never open against a sleeping or half-started API, so this is enforced in three places:

- **In the browser** (`BackendGate`): the app does not mount, and makes no API call, until
  `GET /api/health` returns 200 (server up *and* MongoDB connected). While waiting it shows a
  "Starting FinSight AI" screen with a timer, then continues on its own. A recent successful check
  (10 minutes) skips the wait. While the app is open it pings every 9 minutes so Render's free
  tier does not fall asleep mid-session. After 3 minutes without a response it offers "Try again".
- **On Render:** `healthCheckPath: /api/health` makes Render route traffic only to an instance whose
  database connection is healthy. Production startup also fails fast on bad configuration.
- **Locally:** run `./scripts/dev.sh`. It starts the backend, waits until `/api/health` is healthy
  (up to 90 s, `BACKEND_TIMEOUT` to change), and only then starts the frontend.

Deploy the **backend first**, confirm `/api/health`, then deploy the frontend with `VITE_API_URL` set.

## 3. Frontend on Vercel
1. Import the repo, set **Root Directory** = `frontend` (framework preset: Vite).
2. Environment variable: `VITE_API_URL=https://<your-render-service>.onrender.com/api`.
3. Deploy. `vercel.json` handles SPA routing, long-term caching of hashed assets and security headers
   (it allows the microphone for voice input on your own origin).
4. Add the Vercel URL to the backend's `ALLOWED_ORIGINS` and redeploy the backend.

## 4. Verify
- `GET https://<api>/api/health` → `{"status":"ok","mongodb":"connected"}`
- Startup logs show `Model registry: forecaster v…, agent v…, KB … (… chunks, …)`.
- Sign up on the site, add a month, open **AI Advisor** and ask "What is the PPF lock-in?" — the answer
  should stream with a `[1]` citation.
- Optional live AI check (uses tokens): `cd backend && python -m evals.run_advisor_eval`.

## CI
`.github/workflows/ci.yml` runs backend tests (including the retrieval quality gate) and frontend
lint + build on every push and pull request.
